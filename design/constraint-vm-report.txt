Constraint VM: A BPF-Inspired Safe Evaluator for UI Layout Constraints
======================================================================

Ian Smith and Scott Hudson
March 2026


1  INTRODUCTION
===============

The Mazarin Constraint VM is a small, statically-verified bytecode
interpreter designed to evaluate UI layout constraints safely and
efficiently.  It borrows its safety model from Linux BPF: programs are
compiled from a restricted source language, passed through a static
verifier that proves termination and type safety, and then executed on
a simple stack machine with hard resource limits.  The key difference
from BPF is the domain: instead of packet filtering or kernel tracing,
the programs here compute layout positions, sizes, clamped values, and
other constraint expressions that tie together a reactive attribute
graph in the style of Hudson's Ultra-Lightweight Constraints (ULC).

The system has four layers:

  (1) A restricted subset of Go used as the source language.
  (2) A compiler that parses and type-checks this subset using the
      standard go/parser and go/types packages, then emits bytecode.
  (3) A static verifier that proves safety properties before any
      execution occurs.
  (4) A stack-based interpreter that runs verified programs under
      hard resource caps.

These layers are connected to a reactive attribute library that
implements lazy incremental evaluation: when a source value changes,
dependents are marked dirty and recomputed on demand.  The VM programs
serve as the compute functions inside this graph.


2  THE RESTRICTED GO SUBSET
============================

The source language is Go, but only a small, carefully chosen subset.
The choice of Go is pragmatic: the go/parser and go/types packages
provide a production-quality parser and type checker for free, saving
thousands of lines of custom compiler code.  The restrictions then
carve away everything that would require a runtime, heap allocation,
or unbounded computation.

2.1  What is allowed

  - Types: int64, float64, bool, string, []int64, []float64, []bool,
    []string.  These correspond directly to the VM's tagged value
    types.  No other types exist.

  - Functions: top-level function declarations without receivers.
    Multiple functions are allowed in a single compilation unit; the
    last function is the entry point, and earlier functions serve as
    helpers.  Helper functions may call each other, but not
    recursively.

  - Variables: local variables via := and =.  No package-level
    variables, no globals.

  - Arithmetic: +, -, *, /, % on int64 and float64.  Unary negation.
    String concatenation via +.

  - Comparisons: ==, !=, <, >, <=, >= on int64, float64, and string.

  - Boolean logic: &&, ||, !

  - Control flow: if/else (with arbitrary nesting and else-if chains),
    for-range over collections, break.  Return statements with zero or
    more values.

  - Increment and decrement: i++, i-- as syntactic sugar for
    i = i + 1, i = i - 1.

  - Type conversions: int64() and float64() between numeric types.

  - Collection indexing: coll[i] is mapped to the bounds-checked
    coll_get builtin.

  - Builtin functions: a fixed set of math, string, and collection
    operations (see section 5).

2.2  What is rejected, and why

Every rejected feature falls into one of three categories: it requires
a runtime, it enables unbounded computation, or it introduces
complexity that provides no value for constraint expressions.

Features requiring a runtime:

  - Goroutines and channels.  These require a scheduler.
  - Closures and anonymous functions.  These require heap-allocated
    function values with captured environments.
  - Interfaces and type assertions.  These require runtime type
    information and method dispatch tables.
  - Maps.  These require a hash table implementation.
  - Pointers and address-of (&).  These require a heap and garbage
    collector.
  - make, new, append.  These are allocator calls.
  - defer, panic, recover.  These require stack unwinding machinery.
  - import.  No external code; the program is self-contained.

Features enabling unbounded computation:

  - General for-loops (for i := 0; i < n; i++).  The iteration
    count depends on runtime values and cannot be statically bounded.
    Only for-range over collections is allowed, because the collection
    length is known before the loop starts.  This is the same
    principle as BPF's bounded-loop restriction.
  - Recursion.  Detected and rejected by the verifier's call graph
    cycle check (see section 4.2).
  - goto and labels.  These create arbitrary control flow that
    defeats structured analysis.

Features with no value for constraints:

  - Methods (functions with receivers).  Constraints are pure
    functions of their inputs.
  - Switch statements.  if/else chains suffice; switch adds parser
    complexity for no expressiveness gain in this domain.
  - Slice expressions (s[a:b]).  The take() and drop() builtins
    provide the same functionality with bounds safety.
  - Composite literals ({}).  Collection construction uses builtins.
  - Nested collections ([][]int64).  Layout constraints operate on
    flat data.
  - Select statements.  No channels exist to select on.

The net effect is a language that looks and feels like Go to the
programmer but cannot allocate memory, cannot loop forever, cannot
call arbitrary code, and cannot crash.


3  VM ARCHITECTURE
==================

3.1  Instruction encoding

Each instruction is 128 bits (16 bytes), laid out as:

  bits    field      purpose
  ----    -----      -------
  0-7     opcode     the operation (40+ opcodes)
  8-15    typ        value type tag (I64, F64, Bool, Str, etc.)
  16-31   op1        local slot, builtin ID, function index, or
                     string table index
  32-47   op2        secondary operand (arg count, collection size)
  48-63   flags      reserved for verifier annotations
  64-127  imm        inline constant (int64 or float64 bit pattern)

The fixed-width encoding simplifies both the verifier and the
interpreter: every instruction can be indexed by offset without
variable-length decoding, and the verifier can walk the instruction
stream in a single pass.  The 128-bit width is generous compared to
BPF's 64-bit encoding, but the programs are small (typically 10-50
instructions) and the extra space buys a type tag and a full 64-bit
immediate in every instruction, eliminating multi-instruction
constant loads.

3.2  The operand stack

The VM is a stack machine with a 256-slot operand stack.  Values are
tagged unions:

  type Value struct {
      typ  uint8      // TypeI64, TypeF64, TypeBool, TypeStr, etc.
      i64  int64      // active for I64, Bool (0/1), Tribool (0/1/2)
      f64  float64    // active for F64
      str  string     // active for Str
      coll []Value    // active for collection types
  }

Each operation pops its operands, checks their type tags (defense in
depth--the verifier has already proven they match), performs the
computation, and pushes the result.  Division by zero produces 0
rather than a panic, and all string/collection indexing is bounds-
checked with safe fallbacks.

3.3  Flat locals instead of stack frames

This is the most significant architectural departure from both
conventional VMs and BPF.  A normal VM uses stack frames: each
function call allocates a frame on the stack (or a separate call
stack) to hold its local variables, and deallocation happens on
return.  BPF avoids this entirely by not having function calls in
the classic verifier (though BPF added limited tail calls later).

The Constraint VM takes a third path: a single flat array of 64 local
variable slots, with non-overlapping ranges statically assigned to
each function.  Function 0 might use slots 0-3, function 1 uses
slots 4-7, and so on.  The ranges are computed at compile time by
walking each function's AST to count unique variable names (parameters
plus body locals), then assigning contiguous slot ranges.

This works because of a property unique to the constraint domain:
recursion is forbidden.  The verifier builds the call graph from
OpCall instructions and runs DFS cycle detection; any cycle is
rejected.  Without recursion, each function's locals are live at most
once at any point during execution.  There is no need for a frame
pointer, no need for save/restore of locals on call, and no need for
dynamic stack growth.  The flat array is simply indexed by slot
number.

The tradeoff is that slot usage is the sum of all functions' locals
rather than the maximum.  For constraint programs with 2-4 small
helper functions, this is negligible.  The MaxLocals limit of 64
slots provides ample room.

On function call, the caller's arguments are already on the operand
stack.  The callee's compiled prologue pops them (in reverse, since
the stack is LIFO) and stores them to its local slots.  On return,
the return values are on the operand stack; the caller picks them up
from there.  A small return-address stack (8 entries max) saves and
restores the program counter and operand-stack pointer.

3.4  Control flow

Control flow uses structured markers rather than arbitrary branch
targets:

  IF / ELSE / END_IF     conditional execution
  FOR_RANGE / END_FOR    bounded iteration over a collection
  BREAK                  exit innermost FOR_RANGE

The interpreter handles IF by popping a boolean: if true, execution
falls through into the then-branch; if false, the interpreter scans
forward (tracking nesting depth) to the matching ELSE or END_IF.
Similarly, the ELSE instruction scans forward to END_IF.  This
scanning is O(n) in the worst case but n is small; the simplicity
gained by avoiding a branch-target table is worth it.

FOR_RANGE pops a collection, then executes the body once per element,
setting the index and value locals on each iteration.  The iteration
count is bounded by the collection length--there is no way to
construct an infinite collection.  BREAK exits the innermost loop.

3.5  Resource limits

  limit                    value    enforcement
  -----                    -----    -----------
  instruction counter      100,000  runtime (fuel counter)
  operand stack depth      256      runtime (push checks)
  local variable slots     64       verifier + runtime
  function call depth      8        runtime (retStack)
  control flow nesting     32       verifier

The instruction counter is the primary termination guarantee, just as
in BPF.  Every instruction costs one unit of fuel.  When fuel reaches
zero, execution halts with an error.  In practice, constraint programs
execute 10-100 instructions; the 100,000 limit is a safety net.


4  THE VERIFIER
===============

The verifier performs abstract interpretation over the instruction
stream before any execution occurs.  It is modeled on the BPF
verifier but is simpler because the instruction set is simpler (no
memory access, no maps, no helper calls with complex return semantics).

4.1  Properties proved

Stack safety.  The verifier maintains an abstract type stack (a stack
of type tags, not values) and simulates every instruction's stack
effect.  It proves:

  - No underflow: every pop has a corresponding push.
  - No overflow: the stack never exceeds MaxStackDepth.
  - Consistency at merge points: when two control flow paths join
    (at END_IF or END_FOR), the abstract stacks must have the same
    depth.  If one path returns and the other does not, the returning
    path's stack state is discarded and the non-returning path's
    state continues.

Type safety.  Each entry on the abstract stack carries a type tag.
The verifier checks that arithmetic operations receive numeric types,
comparisons receive comparable types, boolean operations receive
booleans, and so on.  STORE records the type of the stored value, and
LOAD pushes the recorded type.

Initialized locals.  The verifier tracks which local slots have been
initialized (stored to at least once on all paths leading to the
current point).  LOAD from an uninitialized slot is rejected.  At
control flow merge points, the initialization state is the
intersection of both paths: a slot is considered initialized only if
it was initialized on both branches.  This is conservative but sound.

Termination.  All paths must end with RET.  Code after an
unconditional RET is flagged as unreachable.  Unterminated IF or
FOR_RANGE blocks are rejected.

Structural integrity.  IF/ELSE/END_IF and FOR_RANGE/END_FOR must be
properly nested.  BREAK is only valid inside FOR_RANGE.  Maximum
nesting depth is 32.

4.2  Call graph cycle detection

For multi-function programs, the verifier builds an adjacency list
from OpCall instructions and runs depth-first search with the
standard white/gray/black coloring scheme.  Any back edge (a call to
a gray node) indicates a cycle and is rejected with an error message
naming the two functions involved.

This is the critical piece that makes the flat-locals scheme work:
without cycles, each function's locals are guaranteed to be live at
most once.

4.3  Per-function verification

After the call graph check, each function is verified independently.
Its code slice is extracted from the shared instruction stream, and
the abstract interpreter runs over it with the function's parameter
count seeded onto the type stack.  This catches per-function bugs
(uninitialized locals, stack mismatches) independently of the calling
context.

4.4  Comparison with BPF verification

The BPF verifier and the Constraint VM verifier share the same core
idea--prove safety statically so the runtime can skip checks--but
differ in several ways:

  BPF                              Constraint VM
  ---                              -------------
  Register machine (11 regs)       Stack machine (256-deep)
  Tracks value ranges per reg      Tracks type tags per stack slot
  Complex memory access rules      No memory access (no pointers)
  Map access with key/value types  No maps; collections are values
  Helper calls with rich sigs      Builtins with fixed signatures
  No structured loops (until v2)   FOR_RANGE with collection bound
  No function calls (classic)      Multi-function with cycle check
  Millions of instructions         Tens of instructions
  Kernel safety critical           UI-layer safety

The Constraint VM verifier is simpler because the instruction set is
simpler.  BPF must reason about pointer arithmetic, memory bounds,
reference counting, and helper function side effects.  The Constraint
VM has none of these: there are no pointers, no memory operations,
and all builtins are pure functions.  This makes the verifier
straightforward to implement correctly.


5  BUILTIN FUNCTIONS
====================

The VM provides a fixed set of builtin functions that cover the
common operations needed by layout constraints.  These cannot be
written in the restricted Go subset (they require runtime support
for things like sorting), so they are implemented in the interpreter
and called via the CALL_BUILTIN opcode.

Math (int64):    min, max, clamp
Math (float64):  minf, maxf, clampf, sqrt, floor, ceil, round

String:          str_len, str_concat, str_contains, str_substr,
                 str_prefix, str_suffix, str_upper, str_lower

Collection:      coll_len, coll_get, coll_take, coll_drop,
                 coll_sort, coll_concat, coll_page, coll_empty

Additionally, Go's built-in len() is recognized by the compiler and
mapped to either str_len or coll_len depending on the argument type.
The + operator on strings is mapped to str_concat.  Array indexing
(coll[i]) is mapped to coll_get.

All builtins are bounds-safe.  coll_get returns an error on
out-of-bounds access.  str_substr clamps its start and length
arguments to the string's actual bounds.  coll_take and coll_drop
clamp their count to the collection length.


6  THE COMPILER
===============

6.1  Pipeline

The compiler takes a string of restricted Go source and produces a
verified Program struct.  The pipeline is:

  (1) Wrap the source in a package declaration and prepend stub
      function declarations for all builtins.  The stubs are minimal
      Go functions (e.g., "func clamp(val, lo, hi int64) int64
      { return 0 }") that exist only to satisfy the type checker.

  (2) Parse with go/parser.ParseFile.  This produces a full Go AST
      at zero implementation cost.

  (3) Type-check with types.Config.Check.  This produces a
      types.Info struct mapping every AST expression to its resolved
      type.  Again, zero implementation cost for a complete type
      checker.

  (4) Collect user function declarations.  The stub functions are
      filtered out by name.

  (5) Walk each function's AST to count unique local variable names
      (parameters plus body variables).  Assign non-overlapping slot
      ranges.

  (6) Run the restriction checker on each function.  This rejects
      disallowed AST node types (goroutines, closures, for-loops,
      pointers, etc.).

  (7) Generate bytecode for each function.  The code generator walks
      the typed AST and emits instructions, using the type checker's
      output to determine which type variant of each operation to use.

  (8) Run the verifier on the generated program.  This catches any
      bugs in the code generator itself (the "internal compiler error"
      path).

  (9) Return the verified Program.

6.2  Using go/parser and go/types

The decision to use Go's standard library for parsing and type
checking is the compiler's most important design choice.  A custom
parser and type checker for even a simple language is thousands of
lines of code and a source of ongoing bugs.  By using go/parser and
go/types, the compiler gets:

  - Correct, battle-tested parsing of Go syntax.
  - Full type inference, including untyped constants.
  - Error messages with line numbers and column positions.
  - Operator overload resolution (e.g., + on strings vs. integers).

The cost is that the source language must be valid Go syntax.  This is
not a real constraint in practice: the restricted subset is a proper
subset of Go, so any valid constraint program is also a valid Go
program.  The restriction checker then prunes the parts of Go that
are not allowed.

The stub injection technique deserves mention.  The VM's builtins
(clamp, str_len, coll_take, etc.) are not real Go functions.  If the
source calls clamp(x, 0, 100), the type checker will reject it as an
undefined function.  The compiler solves this by prepending stub
declarations:

  func clamp(val, lo, hi int64) int64 { return 0 }
  func str_len(s string) int64 { return 0 }
  ...

These stubs have the right signatures for type checking but are never
executed.  The code generator recognizes calls to these names and
emits CALL_BUILTIN instructions instead.

6.3  Multi-function compilation

A constraint program can contain multiple functions.  The last
function is the entry point; earlier functions are helpers.  The
compiler:

  (a) Builds a function table mapping names to indices.
  (b) Pre-walks all functions to count locals and assign slot ranges.
  (c) Compiles each function sequentially into a shared code stream.
  (d) When the code generator encounters a call to a name in the
      function table, it emits OpCall(funcIndex, argCount) instead of
      CALL_BUILTIN.

Helper functions are useful for decomposing complex constraints.  A
layout constraint that computes both horizontal and vertical position
might factor the common margin calculation into a helper.  The
no-recursion guarantee (enforced by the verifier) means the flat-
locals scheme works without change.


7  INTEGRATION WITH THE ATTRIBUTE SYSTEM
=========================================

The attribute library implements Hudson's lazy incremental evaluation
algorithm.  It has two kinds of attributes:

  Value attributes:       hold a mutable value; calling Set() marks
                          dependents dirty.
  Constraint attributes:  compute their value from dependencies via
                          a closure; recompute lazily when dirty.

The VM integrates through a thin adapter layer.  A VMDep struct pairs
an attribute dependency with a function that extracts its current
value as a VM Value:

  type VMDep struct {
      dep     Noder            // the attribute node (for graph edges)
      extract func() vm.Value  // get current value as VM value
  }

Typed constructors (DepI64, DepF64, DepBool, DepStr) create VMDeps
with the right extraction function.  The NewVMConstraintI64 (and
F64, Bool, Str variants) function creates a constraint attribute
whose compute closure:

  (1) Extracts the current value of each dependency.
  (2) Calls vm.Run with the compiled program and the extracted values.
  (3) Unwraps the first return value.

The attribute graph handles caching and dirty propagation.  When a
source value changes, dependents are marked dirty via a depth-first
walk using a generation counter to handle diamond dependencies.  The
generation counter avoids re-marking nodes that were already visited
in the current walk, which is critical for diamond-shaped dependency
graphs (e.g., a centered child depends on both parent width and its
own width, which also depends on parent width).

An eager evaluation mode forces recomputation immediately after the
dirty walk completes, rather than waiting for the next Get() call.
This is useful for display attributes that must be up-to-date for
the next frame.

Cycle detection in the attribute graph is separate from the VM's
recursion check.  The attribute library maintains an evaluation stack
during Get() calls; if a node appears twice on the stack, a dependency
cycle exists and is reported with the full chain of attribute
locations.


8  TRIBOOL LOGIC
================

The VM supports Kleene three-valued logic (tribool) as a first-class
type.  The three values are false (0), true (1), and unknown (2).
This is not part of the restricted Go subset--tribool values are
constructed by the VM runtime, not by the compiler--but it is part of
the VM's instruction set and is useful for constraint evaluation in
UI systems where some attribute values may not yet be known.

The truth tables follow Kleene's strong logic:

  AND3:  false dominates, then unknown, then true
  OR3:   true dominates, then unknown, then false
  NOT3:  false <-> true, unknown stays unknown
  KNOWN: tribool -> bool (true if not unknown)


9  SAFETY ARGUMENT
==================

The claim is that a verified constraint program will always terminate
and will not corrupt the host system.  Here is the argument:

Termination.  A program can execute at most MaxInstructions (100,000)
instructions before being killed.  Within that budget:
  - The main execution loop decrements a fuel counter on every
    instruction and halts when it reaches zero.
  - FOR_RANGE loops iterate exactly once per collection element.
    The collection is popped from the stack before the loop starts
    and cannot be modified during iteration.
  - Recursion is impossible: the verifier has proven the call graph
    is acyclic.
  - Function call depth is capped at 8.
  - There are no backward jumps in the instruction stream.  The
    FOR_RANGE implementation resets pc to the body start for each
    iteration, but the iteration count is fixed.

Memory safety.  The program cannot access host memory:
  - There are no pointer types and no address-of operator.
  - All values are copied, never referenced.  The VM's Value struct
    is a tagged union stored by value in fixed-size arrays.
  - Stack and local arrays are fixed-size (256 and 64 slots).
  - Collection operations (get, take, drop) are bounds-checked.
  - String operations (substr) are bounds-clamped.

Type safety.  Every operation checks its operand types at runtime
(defense in depth) and the verifier has already proven type
consistency statically.

No side effects.  The program cannot:
  - Perform I/O (no syscalls, no imports).
  - Modify shared state (no globals, no pointers).
  - Allocate memory on the host heap (no make/new/append).
  - Launch goroutines or interact with the scheduler.

The program's only observable effect is its return value.


10  FUTURE WORK
===============

Build-time compilation.  The current system compiles constraint
source at program startup using the full go/parser and go/types
machinery.  A planned cvmc tool will compile .cvmc source files to
Go source files containing var declarations with vm.Program struct
literals, eliminating the runtime dependency on go/parser and
go/types.  This is the same pattern used by protobuf and other code
generators.

Cross-constraint function sharing.  Currently, helper functions are
private to a single constraint program.  Sharing helper functions
across constraints (e.g., a common margin calculator used by
multiple layout constraints) would require a linking step and a
shared function table.

Richer verifier return-type tracking.  The current verifier tracks
argument types precisely but uses an I64 placeholder for function
return types.  Full return-type propagation would catch more errors
statically.


APPENDIX A: ULC OPERATIONS IN RESTRICTED GO
============================================

Hudson's Ultra-Lightweight Constraints paper defines six core
constraint operations for layout.  Each operates in terms of a
value (typically a parent or sibling attribute), the widget's own
width or height (wh), and a constant parameter (parm).  Below, each
ULC operation is expressed as a function in the restricted Go subset
used by this system.

The ULC paper assumes a fixed vocabulary of relationships: self,
parent, previous sibling, next sibling, first child, last child,
max child, min child.  In our system, these relationships are
expressed through the attribute dependency graph: the constraint
function's parameters are the referenced attributes, and the graph
edges are established when the constraint is created.


A.1  plus_offset: value + parm

    Positions a widget at a fixed offset from a reference point.
    Typical use: placing a child at a margin from the parent's edge.

    func PlusOffset(value int64, parm int64) int64 {
        return value + parm
    }

    Example: child.x = parent.x + 10
    Usage:
        parentX := NewValue[int64](100)
        prog := compile("func PlusOffset(...) ...")
        childX := NewVMConstraintI64(prog, DepI64(parentX), DepI64(margin))


A.2  minus_offset: value - parm

    Positions a widget at a negative offset.  Typically used for
    right-to-left or bottom-to-top positioning relative to a
    reference point.

    func MinusOffset(value int64, parm int64) int64 {
        return value - parm
    }

    Example: label.x = parent.right - 20


A.3  centered: (value - wh) / 2 + parm

    Centers a widget within a parent, with an optional offset.
    "value" is the parent's width (or height), "wh" is the widget's
    own width (or height), and "parm" is a centering offset
    (usually 0).

    func Centered(parentSize int64, mySize int64, parm int64) int64 {
        return (parentSize - mySize) / 2 + parm
    }

    Example: button.x = (dialog.width - button.width) / 2
    Usage:
        dialogW := NewValue[int64](400)
        buttonW := NewValue[int64](80)
        offset  := NewValue[int64](0)
        prog := compile("func Centered(...) ...")
        buttonX := NewVMConstraintI64(prog,
            DepI64(dialogW), DepI64(buttonW), DepI64(offset))


A.4  plus_far_off: value - wh - parm

    Positions a widget at a fixed offset from the far edge (right
    or bottom) of a reference.  "value" is the reference extent
    (e.g., parent.x + parent.width), "wh" is the widget's own size.

    func PlusFarOff(value int64, wh int64, parm int64) int64 {
        return value - wh - parm
    }

    Example: close_btn.x = dialog.right - close_btn.width - 5


A.5  minus_far_off: value - wh + parm

    Positions a widget relative to the far edge with a positive
    inward offset.  Less common than plus_far_off; used when the
    offset sense is reversed.

    func MinusFarOff(value int64, wh int64, parm int64) int64 {
        return value - wh + parm
    }


A.6  fill: next_sibling.xy - value - parm

    Sizes a widget to fill the gap between its position and the
    next sibling's position, minus a margin.

    func Fill(nextSibPos int64, myPos int64, parm int64) int64 {
        return nextSibPos - myPos - parm
    }

    Example: content.width = sidebar.x - content.x - 5
    Usage:
        sidebarX := NewValue[int64](600)
        contentX := NewValue[int64](10)
        gap      := NewValue[int64](5)
        prog := compile("func Fill(...) ...")
        contentW := NewVMConstraintI64(prog,
            DepI64(sidebarX), DepI64(contentX), DepI64(gap))


A.7  Compound constraints using helpers

    The ULC paper notes that most layout can be expressed with these
    six operations.  For cases that cannot, it provides an "external"
    escape to heavyweight constraint solvers.  In our system, the
    multi-function support serves a similar role: complex constraints
    can be decomposed into helper functions without needing an
    external solver.

    func horizontalMargin(parentW int64, margin int64) int64 {
        return parentW - 2 * margin
    }

    func verticalMargin(parentH int64, margin int64) int64 {
        return parentH - 2 * margin
    }

    func ContentArea(pw int64, ph int64, margin int64) int64 {
        return horizontalMargin(pw, margin) * verticalMargin(ph, margin)
    }


A.8  Constraint with conditional logic

    The restricted Go subset supports if/else, which goes beyond
    the ULC paper's six fixed operations.  This allows constraints
    that adapt to context:

    func ResponsiveWidth(parentW int64, minW int64, maxW int64) int64 {
        w := parentW - 40
        if w < minW {
            return minW
        }
        if w > maxW {
            return maxW
        }
        return w
    }

    This computes a content width with margins, clamped to a
    minimum and maximum.  In ULC this would require the "external"
    escape; here it is a first-class constraint.


A.9  Constraint with collection iteration

    For-range over collections enables constraints that aggregate:

    func MaxChildWidth(childWidths []int64) int64 {
        result := int64(0)
        for _, w := range childWidths {
            if w > result {
                result = w
            }
        }
        return result
    }

    This computes the maximum width among a set of children,
    corresponding to ULC's "max child" reference but generalized
    to arbitrary aggregation.


APPENDIX B: OPCODE REFERENCE
=============================

Constants:
  CONST_I64    push int64 immediate
  CONST_F64    push float64 immediate (bit pattern in imm field)
  CONST_BOOL   push bool immediate (0 or 1)
  CONST_TRI    push tribool immediate (0, 1, or 2)
  CONST_STR    push string from string table (index in op1)

Locals:
  LOAD         push value from local slot op1
  STORE        pop value and store to local slot op1

Arithmetic (type in typ field):
  ADD          pop two, push sum
  SUB          pop two, push difference
  MUL          pop two, push product
  DIV          pop two, push quotient (0 on divide-by-zero)
  MOD          pop two int64, push remainder
  NEG          pop one, push negation
  ABS          pop one, push absolute value

Comparison (type in typ field, always pushes Bool):
  EQ           pop two, push a == b
  NEQ          pop two, push a != b
  LT           pop two, push a < b
  GT           pop two, push a > b
  LE           pop two, push a <= b
  GE           pop two, push a >= b

Boolean:
  AND          pop two bools, push a && b
  OR           pop two bools, push a || b
  NOT          pop one bool, push !a

Tribool:
  AND3         pop two tribools, push Kleene AND
  OR3          pop two tribools, push Kleene OR
  NOT3         pop one tribool, push Kleene NOT
  KNOWN        pop one tribool, push bool (true if not unknown)

Conversions:
  I64_TO_F64   pop int64, push float64
  F64_TO_I64   pop float64, push int64 (truncation)
  BOOL_TO_TRI  pop bool, push tribool

Control flow:
  IF           pop bool; if false, skip to matching ELSE or END_IF
  ELSE         end of then-branch, skip to END_IF
  END_IF       rejoin point after IF/ELSE
  FOR_RANGE    pop collection; iterate with op1=index slot, op2=value slot
  END_FOR      end of FOR_RANGE body
  BREAK        exit innermost FOR_RANGE

Collections:
  MAKE_COLL    pop op2 elements, push collection of type typ

Calls:
  CALL_BUILTIN call builtin op1 with op2 arguments
  CALL         call function op1 with op2 arguments

Return:
  RET          return op2 values from stack
