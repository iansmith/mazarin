[section] Related Work

Mancini builds on decades of work in user interface toolkits, constraint systems, and rendering architectures. This section identifies the well-known techniques and prior art that Mancini draws from directly.

The rendering subsystem in Mancini uses a DrawContext abstraction that encapsulates 2D drawing operations: shape primitives, path building, fills, strokes, text, and a transform stack. This is a standard approach shared by nearly every modern graphics library. Cairo [Worth and Packard, Linux Symposium 2003] and Skia [Google, 2005] both expose this kind of stateful context API, as does the Go gg library that Mancini targets. There is nothing novel in this layer; it is plumbing.

The neumorphic visual style used by Mancini, where widgets appear raised from, flush with, or inset into a surface via offset Gaussian-blurred shadows, is a design trend that emerged around 2019 [Malewicz, 2019]. The deeper idea of mimicking physical affordances in interface elements traces back to Norman's work on affordances [Norman, The Design of Everyday Things, 1988] and the skeuomorphic tradition in Apple's early iOS interfaces. Mancini implements three depth states (raised, flush, inset) with parameterized shadow offsets and blur radii, which is a clean engineering of the style but not a research contribution.

Input handling in Mancini follows the interactor model introduced by Myers [Myers, ACM TOIS 1990] in the Garnet system. Mancini's mouse state machine tracks press, drag, and release with hit-testing callbacks, which is the same fundamental decomposition Garnet used. The StdMouseFeedback and DetailedHit interfaces are straightforward descendants of this model.

The incremental evaluation strategy used by the constraint system combines lazy evaluation with eager invalidation. This is a direct application of Hudson's Eval/Vite algorithm [Hudson, ACM TOPLAS 1991], which showed that lazy re-evaluation (only recompute when a value is read) combined with eager dirty-marking (propagate invalidation immediately on change) gives optimal performance for one-way constraint systems. The change-gated propagation optimization, where re-evaluation that produces the same result suppresses further dirty-marking of dependents, was described in the same work and is also used by modern reactive systems such as Vue.js and MobX. The constraint system also uses a generation counter to deduplicate dirty walks through diamond-shaped dependency graphs, which is a standard technique in incremental computation.

The one-way constraint model itself, where constraints are imperative functions that read inputs and produce outputs rather than declarative relations solved by a simplex method, follows the tradition established by Garnet and Amulet at CMU [Vander Zanden et al., ACM TOPLAS 2001; Myers et al., IEEE Computer 1990]. The Garnet project demonstrated that one-way, dataflow-style constraints are sufficient for the vast majority of UI layout tasks and avoid the ambiguity and performance problems of solver-based approaches like Cassowary [Badros, Borning, and Stuckey, ACM TOCHI 2001]. Mancini's constraint programs are one-way functions in this tradition.

The concept of a hierarchical URI namespace for naming UI attributes has precedents in Plan 9's file namespace and in D-Bus object paths. The specific use of URI patterns for service discovery is conceptually related to mDNS/DNS-SD, though Mancini applies it within a single-machine constraint system rather than across a network.

[section] The Constraint Virtual Machine

Mancini's layout, sizing, damage tracking, and visibility logic are not hardcoded algorithms. They are programs, written in a restricted subset of Go called vgo, compiled to bytecode, verified at load time, and executed by a stack-based virtual machine. This section describes the VM architecture and the vgo language.

[subsection] Architecture

The VM is a stack-based bytecode interpreter with 128-bit fixed-width instructions. Each instruction encodes an opcode, a type tag, two operand fields, a flags field, and a 64-bit immediate value. The execution model has three address spaces: an operand stack (256 slots) for expression evaluation, a flat local variable array (64 slots) shared by parameters and local variables, and a call stack (8 frames) for intra-program function calls. Parameters occupy the first N local slots; the remaining slots are available for variables declared in the function body. There are no nested scopes. All locals are at function level and addressed by integer index.

The VM has a small set of predefined value types. The scalar types are int64, float64, bool, string, and tribool (a three-valued logic type with true, false, and unknown). There are homogeneous collection types for each scalar. There are also composite types for structured data used in UI work: Rectangle, Point2D, Point3D, PointF2D, PointF3D, Timespec, Timezone, Duration, Date, Radians, Degrees, IPv4, IPv6, ShepherdId, and MazId. Each composite is stored in a fixed 24-byte data field within the Value structure. The type system is closed; user-defined types are not supported.

Builtin functions provide the standard library. There are math operations (min, max, clamp, sqrt, trig functions), string operations (length, concatenation, substring, prefix/suffix testing), collection operations (length, indexing, take, drop, sort, concatenation), rectangle operations (union, intersection, overlap testing, area, width, height), and composite constructors and accessors. Critically, there is also a set of service discovery builtins described in the next section: find, deref, exists, and uri_segment.

[subsection] Determinism and Bounded Execution

Every program run is bounded by a fuel limit of 100,000 instructions. Each instruction decrements a counter; when fuel reaches zero, the program halts with an error. All loops are for-range over collections, so iteration count is bounded by collection length. Recursion is prohibited: the verifier rejects any call graph containing a cycle. These properties together guarantee that every constraint program terminates in bounded time proportional to its input size. This determinism is important for two reasons. First, it means the toolkit can run constraint programs with confidence that they will not hang the UI. Second, it means these programs are safe to run inside an OS kernel, where unbounded computation is unacceptable.

[subsection] Verification

Before a program executes, the verifier performs a single-pass static analysis over the bytecode. It checks that the program is within size limits, that IF/ELSE/ENDIF and FOR/ENDFOR blocks are properly nested, that the operand stack never underflows or overflows, that types are consistent at every operation, that local variable slots are initialized before being read, that all code paths terminate with a return instruction, and that the call graph is acyclic. A program that fails verification cannot be executed. This means the interpreter itself does not need to perform runtime type checks or stack bounds checks, because the verifier has already proven these properties hold.

[subsection] The vgo Language

Constraint programs are written in vgo (VM Go), a restricted subset of Go. The compiler uses Go's own parser and type checker, then emits bytecode. The restrictions eliminate every Go feature that could cause unbounded execution, require heap allocation, or introduce concurrency. Specifically, vgo removes: general for loops (only for-range is allowed), goroutines, channels, select, defer, switch, goto, closures, composite literals, struct field access, pointer dereference, type assertions, address-of, methods, imports, and append/make/new. What remains is a pure, functional-style language with scalar and collection types, if/else, bounded iteration, and function calls.

Because vgo is syntactically valid Go, authors get IDE support, syntax highlighting, and familiar semantics for free. The compiler rejects anything outside the safe subset with clear error messages pointing to the offending construct.

[subsection] A Worked Example: Row Width

The row width constraint illustrates how a real layout computation works in vgo. A Row container needs its width to be the sum of its children's widths plus inter-child spacing. The program uses placeholder strings (_0_ through _4_) that are bound to actual URIs at constraint creation time. The binding _0_ is a find pattern for locating children, _1_ is the URI of the spacing attribute, _2_ is the row's own name (for filtering), _3_ is a URI prefix, and _4_ is a URI suffix for the width dimension.

The program begins by calling hasNoChildren, a library function that uses find() to query the attribute namespace for children whose Parent attribute matches this row's name. If there are no children, it returns a default width of 20. If there is exactly one child, found via hasOneChild, the program extracts that child's name from its URI using uri_segment, constructs the child's width URI by concatenating the prefix, child name, and suffix, dereferences that URI to get the child's width, and returns it plus spacing on both sides. For two or more children, the program iterates over all results from find(), filters to those whose Parent value matches this row's name, constructs each child's width URI, accumulates the sum, counts the children, and adds inter-child spacing of (n-1) times the spacing value. It enforces a minimum width of the first child plus margins.

The key observation is that this program discovers its children dynamically. It does not receive a list of children as a parameter. It queries the namespace at evaluation time, which means children can be added or removed and the constraint automatically adapts. The dependency edges between this constraint and the children it reads are tracked by the VM and updated if the set of children changes.

When mancini's Row.InitLayout creates this constraint, it calls BindStrings to replace the placeholders with concrete URIs. For example, _0_ becomes "attr:///shepherd/42/str/*/layout/Parent", _1_ becomes the URI of the row's spacing attribute, _2_ becomes the row's name like "row-1", _3_ becomes "attr:///shepherd/42/int64/", and _4_ becomes "/layout/Width". The compiled bytecode is then attached to the row's Width attribute as a constraint. Whenever any child's width or parent changes, the dirty propagation system marks this constraint dirty, and the next read triggers re-evaluation.

[section] Novel Contributions

This section describes the aspects of the Mancini toolkit and its constraint VM that, to our knowledge, have no precedent in existing UI toolkits, whether academic or commercial.

[subsection] Constraint Evaluation as Verified Bytecode

No existing UI toolkit compiles constraint expressions to bytecode executed by a dedicated virtual machine. Apple's Auto Layout uses the Cassowary simplex solver [Badros, Borning, and Stuckey, ACM TOCHI 2001]. Flutter and SwiftUI use hardcoded algorithmic tree walks with no user-extensible constraint language. Slint compiles its DSL to native code. Garnet and Amulet used interpreted dataflow constraints but without a bytecode representation or formal verification [Vander Zanden et al., ACM TOPLAS 2001]. The ORCSolver [Jiang et al., CHI 2020] introduced OR-constraints for layout but uses branch-and-bound solving, not bytecode.

As described in the previous section, Mancini compiles constraint programs from vgo source to verified bytecode with guaranteed termination. This representation is portable, safe for kernel execution, and extensible: new layout behaviors are new programs, not new code in the toolkit. The verification step means that constraint programs from untrusted sources can be loaded and executed without risk of hanging or crashing the system. The ultra-lightweight constraint model [Hudson and Smith, UIST 1996] established that constraints should be inexpensive enough to use pervasively; bytecode compilation with load-time verification is a concrete mechanism for achieving this in a multi-process OS where constraint programs may cross trust boundaries.

[subsection] Damage Rectangles as Constraint Programs

Every existing UI toolkit treats damage tracking as an imperative side channel separate from layout. Win32 uses InvalidateRect as a manual API call. Wayland requires clients to call wl_surface_damage_buffer explicitly. GTK and Qt provide queue_draw and update methods that coalesce rectangles imperatively. In all cases, the programmer must decide when and where to invalidate, and the system provides no formal relationship between layout changes and the resulting damage.

In Mancini, damage rectangles are constraint programs executed by the same VM that computes layout. The leaf_damage_rect program compares the current bounds, visibility, content, background color, and text color of an interactor against their last-painted values. If any differ, it returns the union of the current and last-painted bounds as the damage rectangle. If nothing changed, it returns an empty rectangle. The parent_damage_rect program unions its own property changes with the damage rectangles of its children. These programs participate in the same dirty-propagation and change-gating system as layout constraints. When a label's text changes, the dirty mark propagates through the damage rect constraint, which re-evaluates and produces a precise rectangle, which propagates to the parent's damage rect, and so on up the tree. No manual invalidation call is needed anywhere. The damage information is a derived quantity, computed incrementally and precisely.

[subsection] Runtime Service Discovery in Constraint Bytecode

Cassowary, Flutter, SwiftUI, Garnet, and every other constraint or layout system we are aware of resolves dependencies at compile time or widget-tree construction time. A Flutter widget receives its children as constructor arguments. An Auto Layout constraint references specific views by identity. A Garnet formula references specific slots by name at creation time.

Mancini's constraint VM has find, deref, and exists as bytecode-level builtins that query a hierarchical URI namespace at evaluation time. The find builtin takes a pattern with wildcards and returns a collection of URIs matching that pattern. The deref builtins resolve a URI to a typed value, returning the tribool value unknown if the URI does not exist or has a type mismatch. The exists builtin checks whether any attributes exist under a given prefix.

This means a constraint program can discover services, peers, and children that did not exist when the constraint was created. The row width example in the previous section demonstrates this: the constraint discovers its children by querying for attributes whose Parent value matches its own name. If a child is added to or removed from the row, the query result changes, the constraint re-evaluates, and the row's width updates. The dependency edges between the constraint and the attributes it reads are tracked dynamically by the VM's read-set mechanism: after each evaluation, the set of URIs actually accessed is compared against the stored dependency edges, and if they differ, the edges are updated.

This dynamic discovery model enables loose coupling between components. A status bar constraint can query for any running application's title without knowing which applications exist. A window manager can discover available panels. Components can appear and disappear, and the constraints that reference them adapt automatically. This is closer to a reactive service mesh than a traditional layout engine.

[subsection] Kernel-Level Constraint System with VDSO Path

LVGL and Slint run on bare metal or embedded RTOSes, but they are userspace libraries. No existing operating system provides constraint evaluation as a kernel primitive. In Mancini's architecture, the constraint namespace lives in kernel-managed shared memory pages with a pointer-free trie structure. Attribute nodes use sequence locks (seqlocks) for lock-free reads: a writer increments a counter to odd before writing and back to even after, and readers retry if they observe an odd counter or if the counter changed between their two reads.

The planned VDSO (virtual dynamic shared object) path means that a userspace Get() on a clean, non-dirty attribute is a pure memory read from the shared page, with no syscall and no context switch. Only dirty attributes or write operations require a syscall into the kernel. This design means the constraint system scales with the number of attributes that actually change, not the total number of attributes in the system. For a typical UI frame where a mouse position changes and a few widgets update, the vast majority of constraint reads are VDSO-fast while only the handful of changed attributes require kernel involvement.

The kernel enforces ownership: each attribute has an owner (a process or the kernel), and only the owner can write to value attributes. Constraints are read-only. This provides isolation between processes that share a constraint namespace, which is essential in an OS where multiple applications contribute to a shared desktop.

[subsection] Hybrid Inside-Out and Outside-In Layout

Flutter's layout is strictly outside-in: constraints flow from parent to child, sizes flow from child to parent, and the parent sets position. This is clean and single-pass, but it cannot express "make this container as wide as its widest child" without an explicit IntrinsicWidth widget that adds a measurement pass and is flagged as a performance concern. Auto Layout is bidirectional but uses the Cassowary solver, which has super-linear complexity and was abandoned by Apple in favor of SwiftUI's simpler negotiate-and-propose model [Apple WWDC 2018, Session 220]. SwiftUI achieves an "always valid" property but only supports parent-proposes, child-chooses.

Mancini supports both layout directions simultaneously in the same framework. The Column and Row containers use inside-out layout: children publish their sizes into the constraint namespace, and the container's width and height are constraint programs that aggregate those sizes (sum for the stacking axis, max for the cross axis). The ColumnOutsideIn container uses outside-in layout: the parent dictates bounds, and children that do not fit are hidden by setting their Visible attribute to false. Both directions use the same constraint VM, the same namespace, and the same dirty-propagation system. The layout direction is a property of the constraint program bound to a particular container, not a property of the framework. A developer can write a new vgo program that implements a different layout policy, such as a grid or a deck, and bind it to a container without modifying the toolkit.

[subsection] Tribool Unknown Values as First-Class VM Type

No mainstream constraint or reactive UI system has three-valued logic built into its evaluation engine. Reactive systems like MobX and Vue.js use JavaScript's undefined or null, which are untyped sentinels that require defensive checking at every use site. Cassowary has no concept of a missing value; an unsatisfiable system is an error. Flutter layout has no notion of "unknown"; a widget must always return a size.

The constraint VM has a tribool type with dedicated opcodes: And3, Or3, Not3 (Kleene three-valued logic), and Known (which converts a tribool to a bool indicating whether the value is known). The deref builtins return tribool unknown when a URI does not resolve or has a type mismatch. This integrates cleanly with the service discovery builtins: when find() returns results but a deref fails because an attribute was removed between the find and the deref, the constraint produces unknown rather than crashing or returning a stale value. Programs can test for unknown explicitly using the is_unknown builtin and provide fallback behavior. This makes partial initialization, transient unavailability, and cross-process attribute lifecycles first-class concerns in the constraint language rather than edge cases handled by ad hoc null checks.
