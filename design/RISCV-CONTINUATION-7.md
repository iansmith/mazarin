## Issue 1: Clock Displays Zero and Doesn't Move

### Symptom
The clock in dapope's top-right corner shows 0:00 and never advances.

### Root Cause Analysis
There are two time-related syscalls:

1. **Mazzy syscall 1000** (`SyscallGetTime` in `ksyscall/gettime.go`):
   - Calls `ktime.GetTime()` which requires `ktime.Init()` to succeed
   - `ktime.Init()` calls `device.GetClock()` — returns the first Clock device
   - The only Clock driver is **PL031** (`kmazarin/rtc/pl031.go`) with
     compatible string `"arm,pl031"`
   - **RISC-V QEMU virt has no PL031** — it has `"google,goldfish-rtc"` instead
   - So `device.GetClock()` returns `false` → `ktime.Init()` never runs →
     `ktime.GetTime()` returns `(0, 0)` always

2. **Linux syscall 113** (`SyscallClockGettime` in `ksyscall/stubs.go:326`):
   - Uses raw `kirq.ReadCounterValue() / kirq.GetTimerFrequency()`
   - This should return time-since-boot even without an RTC
   - `GetTimerFrequency()` calls `ktimer.Frequency()` which on RISC-V returns
     10000000 (10MHz hardcoded in `ktimer/platform_riscv64.go:31`)
   - This path SHOULD work — it doesn't depend on RTC

### Investigation Steps
1. Determine which syscall dapope uses for the clock display (1000 vs 113)
   - Check `flock/dapope/` for time-related calls
   - If it uses Mazzy syscall 1000, that explains the zero (no RTC → ktime
     uninitialized)

2. If it uses syscall 113, check whether `kirq.ReadCounterValue()` returns
   non-zero on RISC-V by adding a temporary debug print

### Likely Fix
**Option A (if dapope uses Mazzy syscall 1000):**
Write a Goldfish RTC driver (`kmazarin/rtc/goldfish.go`) similar to PL031:
- Compatible: `"google,goldfish-rtc"`
- Registers at MMIO base: TIME_LOW (0x00), TIME_HIGH (0x04) — returns
  nanoseconds since epoch
- Register it in `kmazarin/device/registry.go`
- Then `device.GetClock()` succeeds → `ktime.Init()` works → clock advances

**Option B (simpler, if dapope uses syscall 1000):**
Make `ktime.Init()` work without an RTC by using tick counter alone:
- If no Clock device, set `baseSeconds = 0, baseTicks = currentTicks`
- Time starts at epoch 0 but at least advances

**Option C (if dapope uses syscall 113):**
Debug why `ReadCounterValue()` might return 0 on RISC-V (unlikely since timer
IRQs work)

## Issue 2: Spinlock Panic and PU000F192C Page Fault Flood

### Symptom
After running for ~30-60 seconds, the system crashes with:
```
panic: spinlock: failed to acquire after 2μs timeout
fatal error: panic on system stack
```

Before the panic, there's a massive flood of `PU000F192C` debug breadcrumbs —
thousands of entries showing repeated page faults at the same user-space address.

### Stack Trace
```
ds.(*Spinlock).Lock(0x439cbe00)
  kmazarin/ds/spinlock.go:134
main.checkThreadPreemptionImpl(0x439c5b60, 0xfffffffe8000bac0)
  kmazarin/kmazarin/threads.go:2152
main.checkThreadPreemptionInternal(...)
  kmazarin/kmazarin/threads.go:2060
main.checkThreadPreemptionInternal(0x0)
  <autogenerated>:1
runtime.freezetheworld()
  runtime/proc.go:1195
```

### Analysis
1. `freezetheworld()` is called by Go runtime during a fatal error/panic
2. It calls `checkThreadPreemptionInternal` (through autogenerated ABI wrapper)
3. `checkThreadPreemptionImpl` tries to acquire `schedulerLock` at line 2152
4. The lock is already held → 2μs timeout → spinlock panic → cascade

**The real question: what triggers the FIRST fatal error?**

The `PU000F192C` flood precedes the crash. Each `PU` entry likely represents:
- `P` = page fault handler entered
- `U` = user-mode fault (SPP=0)
- `000F192C` = faulting address (or PC) in user space

This suggests one of the userspace programs (probably dapope) is hitting the same
page fault repeatedly. Possible causes:
- A demand-paging bug that doesn't actually map the page on RISC-V
- The faulting address is beyond any mapped region (stack overflow, bad pointer)
- The address 0xF192C is a code address that's in an unmapped part of the ELF

Eventually this flood exhausts something (memory? scheduler time?) causing a
kernel panic, which calls `freezetheworld`, which tries to acquire the
already-held scheduler lock.

### Investigation Steps
1. **Identify what 0x000F192C is** in the dapope or stdio ELF:
   ```bash
   bin/target-objdump -d build/flock/dapope.elf | grep -A2 "f192c:"
   bin/target-objdump -d build/flock/stdio.elf | grep -A2 "f192c:"
   ```
   Or check if it's a data address vs code address.

2. **Check the RISC-V page fault handler** (`exceptions_riscv64.s`):
   - Does it properly handle demand paging for user faults?
   - Does it distinguish instruction faults (scause=12) vs load faults
     (scause=13) vs store faults (scause=15)?
   - Does `handlePageFault` (Go function) correctly allocate and map the page?

3. **Check whether the flood causes a secondary crash**:
   - The repeated `PU000F192C` could be timer interrupts interleaving with page
     fault handling, each trying to preempt
   - If the scheduler lock is held during page fault handling and a timer
     interrupt fires, the timer handler's preemption check would deadlock on
     the scheduler lock
   - On RISC-V, interrupts should be disabled during trap handling (sstatus.SIE
     cleared by hardware), but check if anything re-enables them prematurely

4. **Check if `freezetheworld` → `checkThreadPreemptionInternal` is correct**:
   - `freezetheworld` calls `checkThreadPreemptionInternal` via Go runtime hooks
   - On our kernel this tries to acquire the scheduler lock
   - If the timer ISR already holds it, this deadlocks
   - May need to make `checkThreadPreemptionInternal` handle the panic case
     differently (e.g., skip lock acquisition if in panic state)
